# E7G-T Unified Geometry-Thinking Kernel

> **Canonical public definition.** E7G-T is a geometry-first modelling language and practical calculus for making construction, projection, preservation, loss, reconstruction, operational sameness, material boundaries, transition paths, bridge mode, and admissible use visible.

> **Canonical practical question.** What is being modelled, what does the current representation preserve or lose, which differences matter for this inquiry, and what is the next responsible move?

Capitalised **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** state obligations on conforming analyses, reports, implementations, or validators.

---

## 0. Status and posture

E7G-T v0.10-UC1 integrates two complementary routes:

1. the **extensional–projective route**, governing construction, order-role placement, viewing, projection, preservation, loss, transformation, reconstruction, and bridge discipline; and
2. the **operational-phase route**, governing inquiry-relative sameness, phase classification, material boundaries, typed transitions, path choice, operation order, representative dependence, and abstraction stability.

E7G-T is a modelling and reasoning discipline, a practical calculus, and a candidate reference semantics for machine-checkable implementations.

It is not established mathematics as a whole, empirical physics, a proof system, a universal ontology, a Theory of Everything, an authority decision, performed work, or a replacement for mature domain methods.

### Smallest-use rule

> Use the smallest route and output profile that changes the next responsible move without hiding material risk.

Do not construct a phase geometry when a direct correction, ordinary invariant check, projection-loss note, or established domain test already determines the action.

## 1. Shared constitutional core

Before using either route, declare as much of the following as the use requires:

- **modelled entity** — the thing, system, text, state, relation, or claim under consideration;
- **semantic context** — the local frame in which terms and relations have meaning;
- **inquiry** — the purpose that determines which differences matter;
- **configuration description** — a bounded relational description admitted for the inquiry;
- **model boundary** — what is included and excluded from that description;
- **admissibility conditions** — which configurations, changes, evidence, and comparisons are permitted;
- **intended use** — what the result may support;
- **support posture** — stipulation, formal derivation, observation, calibration, operational validation, mixed, or none;
- **stop or source-return condition** — when classification or reliance must stop, downgrade, or reopen the source.

### Strict distinctions

```text
entity ≠ description
view ≠ source
projection ≠ reconstruction
configuration ≠ phase
phase relation ≠ transition history
classification ≠ world transformation
publication ≠ evidence
status display ≠ performed work
formal notation ≠ proof
```

## 2. Route selection

Use the **extensional–projective route** when the main question concerns:

- construction, extension, or composition;
- D-order placement;
- boundary selection;
- viewing or projection;
- preservation and loss;
- source reconstruction;
- transformation and transformation invariants;
- bridge mode and claim strength.

Use the **operational-phase route** when the main question concerns:

- which non-identical configurations count as equivalent;
- which change crosses a material boundary;
- transition admissibility or reachability;
- path choice or operation order;
- representative dependence;
- whether one operation applies uniformly to an abstraction class.

Use the **combined route** when a view, translation, summary, dashboard, AI answer, interface, or measurement is being used to infer operational status.

## 3. Boundaries

The unified kernel distinguishes four boundary functions.

### 3.1 Model boundary

Determines which entities, relations, values, histories, and unknowns belong to the configuration description.

### 3.2 Admissibility boundary

Determines which configurations, comparisons, evidence, and changes are admitted for the inquiry.

### 3.3 Phase boundary

Separates configurations that are not equivalent under the pinned phase criterion.

### 3.4 Bridge boundary

Marks a change of domain, substrate, authority, empirical posture, or admissible claim strength.

Crossing one boundary does not imply crossing the others.

## 6. Extensional–projective calculus

### 6.1 Primitive moves

1. **Place** — declare entity, optional order role, temporal posture, context, and inquiry.
2. **Bound** — declare the model boundary.
3. **Incide** — declare a typed relation.
4. **Extend** — construct richer declared structure.
5. **Slice** — select a local or contextual view.
6. **View/Project** — render selected or reduced structure.
7. **Preserve/Lose** — name what survives, disappears, or may distort.
8. **Transform** — apply a typed change under declared conditions.
9. **Reconstruct** — identify the candidate source family compatible with the view.
10. **Bridge/Stop** — declare cross-domain posture or stop the claim.

### 6.2 Compact notation

```text
X : Dn @ TRi / C ; I
∂model(X) = B
A ⋈_C B
X ↑ n
S_C^s(X)
View_C(X) = v
π_C^{n→k}(X) = v
ρ_C(v) ⇒ {Γ_i}
τ_kind(X) = Y
Inv_T(X) = J
β_M^{A↔B}
Stop(reason)
```

Notation records discipline. It does not create discipline.

### 6.3 Projection laws

1. Extension is not projection.
2. Projection is not reconstruction.
3. Reconstruction is set-valued by default.
4. Projection loss accumulates and cannot be silently regained.
5. Slice and projection need not commute.
6. An invariant claim requires a declared transformation class.
7. A view may be useful without being source-identifying.

## 7. Typed-change discipline

A visible difference MUST be typed before it is interpreted as a transition.

Canonical change kinds include:

- `worldTransformation`;
- `configurationRevision`;
- `viewing`;
- `orderProjection`;
- `retargeting`;
- `reframing`;
- `classification`;
- `observationUpdate`;
- `composition`;
- `decomposition`;
- `workOccurrence`;
- `dynamicsModelUpdate`.

### Change rules

- Reclassification does not by itself change the modelled world.
- A new view does not by itself change the source.
- A configuration revision may change a description without changing the represented entity.
- Retargeting changes the entity of concern or target kind and requires a declared bridge.
- Work occurrence requires evidence of occurrence; a plan, method description, or status display is not work.

## 8. Operational-phase calculus

### 8.1 Operational phase

> An operational phase is an inquiry-relative equivalence class of admitted configuration descriptions.

Let `A_I` be the admitted configuration family for inquiry `I`, and let `Q` be a pinned phase criterion. Then:

```text
Γ_a ≈_Q Γ_b
```

means that `Γ_a` and `Γ_b` count as operationally equivalent for the inquiry.

The criterion MUST identify:

- admitted configuration family;
- tolerated differences;
- protected relations, invariants, behaviours, interfaces, or action signatures;
- classification aspect: structural, epistemic, operational readiness, or combined;
- support basis and support status;
- intended and non-intended uses.

### 8.2 Equivalence obligations

Where a true equivalence class is claimed, the criterion SHOULD establish or explicitly assume:

- reflexivity;
- symmetry;
- transitivity.

When these conditions are not established, use a weaker relation such as compatibility, similarity, reachability, or provisional grouping rather than calling the result a phase.

### 8.3 Phase boundary

A typed change `λ : Γ_s → Γ_t` crosses a phase boundary when:

```text
Γ_s ≉_Q Γ_t
```

The boundary claim MUST identify the change kind, source and target configurations, criterion, broken or created conditions, support, and next move.

### 8.4 Phase transition

A phase difference does not prove that a transition occurred. A phase transition additionally requires:

- a typed change or path;
- admitted source and target configurations;
- evidence or derivation supporting the occurrence or proposal;
- a boundary result under the pinned criterion.

### 8.5 Representative dependence

An operation claimed at phase level MUST be checked against the relevant representatives.

If members of one input phase can produce outputs in different phases under the same operation, the operation is representative-dependent and cannot be treated as a well-defined phase-level map without additional conditions.

### 8.6 Operation order

For operations `f` and `g`, do not assume:

```text
f ∘ g = g ∘ f
```

Compare the resulting configurations and protected effects. If the paths produce different phase outcomes, order is materially significant.

## 9. Combined projection-to-phase calculus

Let:

- `v` be a visible view;
- `π` be its viewing or projection account;
- `Rec_π(v)` be the admitted reconstruction fibre;
- `Q` be the phase criterion.

Define:

```text
PhaseCandidates_Q(v) = { [Γ]_Q | Γ ∈ Rec_π(v) }
```

### 9.1 One phase candidate

When the supported reconstruction fibre lies in one phase, the view may support classification within the declared evidence and use limits.

### 9.2 Several phase candidates

When the fibre spans several phases, the view is not phase-sufficient.

Required moves include:

- abstain;
- narrow the claim;
- return to source;
- obtain another view or measurement;
- strengthen evidence;
- revise the boundary or criterion.

### 9.3 No admitted candidates

When no admitted configuration explains the view, repair the source family, model boundary, projection account, evidence assumptions, or phase criterion. Otherwise stop.

### 9.4 Unknown fibre

When the reconstruction fibre cannot be responsibly bounded, the phase result is `undetermined`. Formal-looking output MUST NOT hide this uncertainty.

### 9.5 Phase-sufficiency rule

A view supports phase classification only when:

1. the reconstruction fibre is adequately bounded for the inquiry;
2. the fibre is phase-stable or the residual spread is explicitly handled;
3. the support basis is sufficient for the intended use;
4. the view has not crossed an undeclared context, inquiry, or bridge boundary.

## 10. Invariants

### 10.1 Transformation invariant

A property or relation preserved under a declared transformation class.

```text
Inv_T(X) = J
```

### 10.2 Phase-defining condition

A relation, invariant, behaviour, interface, canonical signature, or permitted-action profile used by the phase criterion.

A transformation invariant is not automatically phase-defining. A phase criterion is not required to consist only of universal invariants.

### 10.3 Protected effect

A condition that a proposed path or operation is required to preserve, weaken no further than a declared tolerance, or intentionally create or break.

## 11. Bridge modes and claim strength

| Mode | Supported posture |
| --- | --- |
| `none` | internal modelling only |
| `contemplative-what-if` | exploration, reflection, fiction, ideation |
| `philosophical-interpretation` | conceptual interpretation without formal or empirical force |
| `formal-analogy` | structural resemblance under declared mapping |
| `formal-compatibility` | comparison or mapping to a recognised formal substrate |
| `formal-proof` | proof discharged in a declared formal substrate |
| `empirical-testable` | observation, measurement, prediction/constraint, falsification, evidence |
| `authority-source-linked` | scoped reliance on a competent authority or official source |

### Bridge laws

- A bridge inherits its weakest supported component.
- Rhetoric does not upgrade claim strength.
- Empirical language requires an empirical bridge.
- Authority-looking language requires a valid authority and scope path.
- Neighbourhood, analogy, and compatibility are not identity.

## 13. Proof-of-Path

Proof-of-Path records the accountable route by which a claim, model, proof, output, or phase classification reaches a stated reliance tier.

It records:

- entity, context, inquiry, assumptions, and definitions;
- transformations, views, and projection events;
- obligations created and discharged;
- preservation, loss, and reconstruction status;
- phase criteria and phase results where used;
- evidence and checks;
- bridge mode, claim strength, and weakest link;
- unresolved obligations and stop conditions.

Proof-of-Path may include a formal proof. It is not itself a formal proof unless a declared substrate checks the proof.

## 14. Core laws

1. **Frame before operation.** Declare entity, semantic context, and inquiry before material modelling moves.
2. **Typing before inference.** Type the entity, relation, change, and support posture before relying on them.
3. **Extension is not projection.** Construction and representation are different directions.
4. **Projection is not reconstruction.** A view does not uniquely recover its source by default.
5. **Configuration is not phase.** A phase is a criterion-relative class, not a single state.
6. **Difference is not transition.** Distinct phases do not establish a historical or causal path.
7. **Boundary is plural.** Model, admissibility, phase, and bridge boundaries must not be silently merged.
8. **Phase classification is inquiry-relative.** Changing the inquiry may change the phase criterion without changing the world.
9. **Phase-level operations require representative checks.** Hidden representative dependence blocks uniform abstraction.
10. **Path order may matter.** Non-commuting operations require explicit path comparison.
11. **A view must be phase-sufficient before classification.** Several phase candidates require abstention or source return.
12. **Bridge claims inherit the weakest link.** No component may silently upgrade the whole claim.
13. **Empirical language requires empirical bridge.** Measurement, prediction/constraint, falsification, and evidence are required.
14. **Mature domain tools govern their domain.** E7G-T frames and routes; it does not bypass stronger methods.
15. **The next move is the practical test.** If the analysis does not change inspection, repair, testing, comparison, reliance, or stopping, ordinary prose may be preferable.

## 15. Failure-mode linter

Check for:

- entity/description confusion;
- semantic context and inquiry conflation;
- D7 used as a universal context container;
- hidden model-boundary shift;
- hidden admissibility change;
- phase criterion not pinned;
- ordinary similarity mislabeled as equivalence;
- phase difference mislabeled as transition;
- viewing or revision mislabeled as world transformation;
- projection loss denial;
- unique reconstruction claimed without rival elimination;
- phase classification from a fibre spanning several phases;
- invariant without transformation class;
- phase-defining condition confused with universal invariant;
- representative dependence hidden by abstraction;
- operation order assumed to commute;
- support status mixed with structural effect;
- formal notation mistaken for proof or evidence;
- status display mistaken for work, readiness, approval, or authority;
- bridge inflation;
- empirical language without empirical bridge;
- missing stop, source-return, or reopen condition.

## 16. Minimal worked examples

### 16.1 AI answer

A fluent answer is a D2 textual view. Its reconstruction fibre may include unsupported memory, source-linked synthesis, current verified evidence, or expert-validated conclusions. If these candidates span different reliance phases, the answer is not phase-sufficient. Required move: source return or current verification.

### 16.2 Translation

Two target wordings may preserve the same legal modality and remain phase-equivalent. Replacing discretionary `may` with mandatory `shall` may cross the legal-force phase boundary even when the sentence remains fluent and grammatically correct.

### 16.3 Dashboard

A green metric can be compatible with a genuinely healthy system, stale data, gaming, hidden downstream failure, or an unsuitable threshold. If these configurations occupy different readiness phases, the dashboard view cannot determine readiness without another view or source return.

### 16.4 Software refactoring

A refactoring is not behaviour-preserving merely because unit tests pass for one representative. The operation must preserve the phase criterion across the admitted representative family or disclose representative dependence.

### 16.5 Proof interface

A visible “accepted” state may hide assumptions, admitted axioms, unresolved explanation duties, or a distinction between proof checking and human understanding. The interface state must not be treated as phase-sufficient for every proof-use inquiry.

### v1.0 gate

Do not advance to v1.0 until:

- shared terminology and typed changes are stable;
- phase criteria and view-sufficiency rules survive pilot testing;
- representative and path checks are tested in real cases;
- legacy applications are re-authored rather than mechanically renamed;
- software schemas and validators are tested;
- public language is simplified without erasing critical distinctions;
- at least one external reviewer can apply the combined route without author assistance.
